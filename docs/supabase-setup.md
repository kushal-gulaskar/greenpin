# Set up a restricted Supabase development project

1. In the Supabase Dashboard choose **New project**, select your development organization and free plan, choose a region, and create a database password in your password manager. Wait for the project to become ready.
2. Use a fresh development database. In **SQL Editor → New query**, run the complete contents of `supabase/migrations/001_trees.sql` once. In a second query run `002_cloud_registry.sql`. Each file is transactional. Alternatively use your team's Supabase CLI migration workflow in version order. Choose one migration tracking method for that environment.
3. Migration 002 expects a new or empty Sprint 1 SQL table. It stops the transaction if that table already has rows. An existing populated SQL deployment needs a reviewed backfill. Browser records use the separate import screen.
4. Verify in Table Editor that profiles, trees, and the history tables exist. In **Storage → tree-photos** check that the bucket is private, has a 10 MB limit, and permits JPEG, PNG and WebP. PostGIS is installed under the extensions schema. The project Data API must expose public tables and functions for authenticated clients.
5. Open **Connect** for the project URL and **Settings → API Keys** for the publishable key beginning with `sb_publishable_`. Copy `.env.example` to `.env.local` and set `VITE_DATA_SOURCE=supabase`, `VITE_SUPABASE_URL`, and `VITE_SUPABASE_PUBLISHABLE_KEY`. Vite includes public environment variables in browser code. Keep database passwords, provider credentials and privileged server keys in their administrative environments. [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys)
6. Configure two development test numbers as described in [Authentication](authentication.md). Restart Vite. Open the app, sign in, and check that your profile appears. An empty dashboard is expected for a new account. Run the [hosted acceptance suite](security-testing.md) before relying on the configuration.
